## Overview

この Skill は、巨大なコードベース（モノリス、巨大サービス、複数パッケージのリポジトリなど）を対象に、

* パッケージ・ディレクトリ構造のレイヤー分解
* フレームワーク／外部境界とドメインロジックの境界の特定
* 主要コンポーネント・モジュール・「リソース」に相当する単位の棚卸し
* 変更影響範囲の大きいホットスポットの抽出
* 新しく join したエンジニアに提示できる「読むべき順番」の設計

を Claude に実行させるためのプロンプトと手順をまとめたものです。

Claude は、この Skill が有効な場合、大規模リポジトリの理解・改修・バージョンアップ調査を行う際に、この Skill を読み込んでから解析を進めてください。

---

## When Claude should use this Skill

Claude は、次のような状況でこの Skill を優先的に利用してください。

* 規模の大きいコードリポジトリ（バックエンド、フロントエンド、ライブラリ、モノレポなど）の全体構造を理解したいとき
* コードベース全体のレイヤー構造やホットスポットを把握したいとき
* 新しく join したエンジニア向けに「どこから読めばよいか」を設計したいとき
* 大規模リファクタリングやバージョンアップ前に、影響範囲を事前に把握したいとき

個々の関数やクラス単位の説明だけが目的の場合ではなく、**リポジトリ全体を構造的・俯瞰的に理解したいとき**にこの Skill を使ってください。

---

## Assumptions

* 対象リポジトリは、ある程度の規模があり、複数のディレクトリ／パッケージ／モジュールで構成されていることを前提とします。
* Web アプリケーション、API サーバ、ライブラリ群、インフラコード（例: Terraform）、モノレポなど、構造がレイヤー化されているコードベースを想定します。
* Claude は対象リポジトリ一式にアクセス済みであること（Code モード等で読み込み済みであること）を前提とします。

---

## Workflow Overview

Claude がこの Skill を使うときは、次の 3 ステップで解析を行ってください。

1. **構造抽出 (Structural Extraction Skill)**

   * ディレクトリ・パッケージ構造を「層」に分解し、外部境界／ドメイン／インフラなどの役割を整理する

2. **レイヤリングと読み順設計 (Layering Skill)**

   * 初見者が読むべきファイル・ディレクトリの優先順位を決め、「最短で全体像に到達する読み順」を設計する

3. **棚卸しとホットスポット抽出 (Inventory Skill)**

   * 主要コンポーネント・モジュールの棚卸しと、変更影響範囲の大きい箇所の特定を行う

以下に、それぞれのステップで Claude が使うべきプロンプトテンプレートを記載します。

---

## Step 1: Structural Extraction Skill（構造抽出）

巨大リポジトリの「地図」を作るステップです。
Claude は、対象リポジトリの構造を次のような一般的なソフトウェアレイヤーに分類してください。

※ 特定のフレームワーク（例: Rails, Next.js, Terraform など）に特化せず、コードから役割を推定して分類してください。

### Prompt template

```txt
このコードリポジトリ全体の構造を解析し、次の観点でレイヤーに分類してください。

1. エントリポイント層
   - 実行エントリ（例: main 関数、サーバ起動コード、CLI エントリ、フレームワークの起動ポイントなど）

2. フレームワーク・外部境界層
   - Web フレームワークや外部 SDK／ライブラリとの境界
   - ルーティング、コントローラ、ハンドラ、アダプタなど

3. ドメインロジック層
   - ビジネスロジック、ユースケース、サービス層、ドメインモデルなど

4. インフラ層
   - DB アクセス、メッセージング、キャッシュ、設定、接続管理、ロギング、エラーハンドリングなど

5. 共通ロジック／ユーティリティ層
   - ヘルパー、ライブラリ、共通関数、共通クエリビルダ、共通コンポーネントなど

6. テスト層
   - 単体テスト、統合テスト、エンドツーエンドテストなど

各レイヤーごとに、次を出力してください：
- 含まれるディレクトリ・パッケージ・主要ファイルの一覧
- それぞれの役割と責務
- 他レイヤーとの依存関係（どのレイヤーに依存しているか、依存方向）

必要に応じて、上記以外のレイヤー区分が妥当であれば追加して構いません。その場合は理由も説明してください。
```

Claude は、このステップの結果をもとに、以降の解析で「どのレイヤーにフォーカスすべきか」を判断してください。

---

## Step 2: Layering Skill（レイヤリングと読み順設計）

このステップでは、「初めてこのコードベースを触るエンジニアが、最短で全体像を掴む読み順」を設計します。

### Prompt template

```txt
このコードベースを初めて理解するエンジニアが、1〜2 日で全体像を掴み、
安全に小さな変更を加えられる状態になることを目標とします。

その前提で、「読むべきファイル・ディレクトリの優先順位リスト」を作成してください。

各項目について、次の観点で理由を説明してください：
- そのファイル/ディレクトリが全体構造の理解にどの程度寄与するか
- 依存関係のハブになっているか（多くのコンポーネントから参照されているか）
- 変更影響範囲が広いか（ここを変えるとどこまで波及しうるか）
- ドメイン知識やビジネスロジックの理解にどれだけ貢献するか

最終的なアウトプットは、次の形式で提示してください：

1. 読むべき順番付きのリスト（Top 10〜15 項目）
2. 各ステップで着目すべき観点
   - 例: フレームワークの使い方 / ルーティング構造 / ドメインモデル / インフラの接続まわり など
3. 初手ではあえて読まなくてよい詳細箇所
   - 最初の段階では後回しにしてよい実装詳細や補助的なユーティリティ群
```

Claude は、Step 1 で得たレイヤー情報を使って、読み順を構造的に説明してください。

---

## Step 3: Inventory Skill（棚卸し・ホットスポット抽出）

このステップでは、コードベース全体を俯瞰して「何がどこにあるか」と「どこが危険か」を明確にします。

### 3-1. コンポーネント／モジュール棚卸し

ここでは、「このリポジトリにおける単位」を柔軟に解釈してください。
例：サービス、モジュール、パッケージ、主要クラス／コンポーネント、Terraform リソース、API エンドポイントなど。

```txt
このコードベースにおける主要なコンポーネント／モジュール／機能単位を棚卸ししてください。

次の情報を表形式で整理してください：

- 名前（例: UserService, AccountController, order module など）
- 種別（サービス／モジュール／ライブラリ／UI コンポーネント／インフラコード など）
- 主な責務（1 行で要約）
- 実装のエントリポイントとなるファイル・ディレクトリパス

ドメインレベルで似た責務を持つコンポーネントがあればグルーピングし、
「このグループを理解すると他も芋づる式に理解しやすい」という観点で
優先度を付けてください。
```

### 3-2. ホットスポット抽出

変更が広範囲に波及する「危険な結節点」を洗い出します。

```txt
このコードベース全体を分析し、変更が広範囲に波及する可能性が高い
「ホットスポット」を抽出してください。

区分の例：
1. 設定・接続まわり（config, connection, environment 周り）
2. 共通インフラ層（DB アクセス、メッセージング、キャッシュクライアント、認証基盤など）
3. フレームワークや外部サービスとの境界（アダプタ、ゲートウェイ、API クライアント）
4. 多数のコンポーネントから参照されるユーティリティ／ライブラリ
5. ドメイン的に重要かつ依存が集中しているモジュール（例: 課金ロジック、認可ロジックなど）

各ホットスポットについて：
- 具体的なファイル名・ディレクトリ・クラス／関数名
- 直接依存しているコンポーネント
- 間接的に影響を受ける可能性のあるコンポーネント
- 人間が見落としやすい依存パターン（例: グローバル設定、イベント購読、暗黙の共有状態）

を説明してください。
```

## Pitfalls and Limitations

Claude は、この Skill を使う際、AI の限界とリスクについても明示的に考慮してください。

* 横断的なロジック（ロギング、メトリクス、トレース、エラーラッピング、Feature Flag など）は解析から漏れやすい
* テストコードから推測した仕様が、実運用の前提とずれている可能性がある
* 動的ディスパッチやリフレクション、コード生成を多用しているコードベースでは、静的な構造解析だけでは依存関係を過小評価しやすい
* パフォーマンス・セキュリティ・運用上の意図は、コード構造だけからは復元できない場合がある

Claude は、**構造の抽出・整理・可視化に集中し、設計意図や最終的な判断は人間のエンジニアに委ねるべき**であることを忘れないでください。

## Example Usage

ユーザーが次のように指示した場合、この Skill を読み込み、Step 1〜3 のフローを実行してください。

* 「この巨大リポジトリの構造を把握したい」
* 「このプロジェクトのどこからコードを読めばいいか教えて」
* 「このサービス全体の変更影響範囲を事前に洗い出したい」
* 「新しく join するメンバー向けに、読むべきコードの順番を設計したい」

これらのケースでは、まず Step 1 の構造抽出を行い、その結果をもとに Step 2, Step 3 を順に実行してください。
